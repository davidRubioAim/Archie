GUÍA RÁPIDA DE MANTENIMIENTO - AIM AUTO ARCH (ARCHIE)
=========================================================

1. ¿DÓNDE ESTÁ CADA COSA?
---------------------------------------------------------
- /Core/   -> Código fuente del programa. 
- /Assets/ -> Imágenes, logos y tipografías.
- /Config/ -> Archivos de configuración (stadium_library.json).
- /versions/ -> Carpeta generada automáticamente. Aquí es donde el launcher guarda y ejecuta el código descargado de GitHub. NO trabajes ni edites archivos aquí dentro.
- Archie.bat -> Tu lanzador local con tu clave privada (NUNCA se sube a GitHub).
- launcher.py -> El script que revisa si hay actualizaciones en GitHub y las descarga.

2. CÓMO AÑADIR O EDITAR ESTADIOS (O CÓDIGO)
---------------------------------------------------------
1. En tu carpeta principal de trabajo, ve a /Config/
2. Edita stadium_library.json copiando el bloque de un estadio existente y cambiando sus valores.
3. Guarda el archivo.
NOTA: Como el programa se ejecuta desde lo que descarga de GitHub (carpeta /versions/), no verás estos cambios en la app hasta que los subas y lances una actualización.

3. CÓMO GUARDAR TUS CAMBIOS EN GITHUB (COMMIT)
---------------------------------------------------------
Abre la terminal en la raíz de tu proyecto y ejecuta:
1. git add .
2. git commit -m "Añadidos nuevos estadios y arreglos visuales"
3. git push
(Con esto, tu código de trabajo ya está a salvo en la nube de GitHub).

4. CÓMO LANZAR UNA NUEVA VERSIÓN (ACTUALIZACIÓN AUTOMÁTICA)
---------------------------------------------------------
Para que tu ordenador (y el de cualquier otro usuario) descargue los cambios:
1. Ve a tu repositorio en la web de GitHub.
2. Crea un nuevo "Release" (o Tag) con el nuevo número de versión, por ejemplo: v0.26
3. Ve a tu Gist de GitHub (el enlace crudo de version.json).
4. Edita ese Gist cambiando el texto a "v0.26" y guárdalo.

¡Listo! La próxima vez que abras Archie.bat, el launcher leerá el Gist, verá que hay una versión v0.26, la descargará de GitHub, y la instalará sola.

---------------------------------------------------------
REGLA DE ORO: Mantén Archie.bat y cualquier archivo .env en tu archivo .gitignore para proteger tu clave de inteligencia artificial.

1. El Concepto General
MEGA STRIP Generator Pro es una herramienta de automatización Broadcast diseñada para resolver uno de los problemas más tediosos y propensos a error en la producción de publicidad para estadios: la adaptación a múltiples resoluciones de pantallas LED perimetrales (U-Televisiva).

En lugar de que un diseñador monte a mano el archivo gigantesco (Mega Strip) y luego lo trocee manualmente en After Effects para que lo entienda el servidor del estadio (System File), este software lo hace todo en segundos, garantizando una precisión matemática impecable.

2. La Arquitectura del Software (Los Archivos)
El programa se ha diseñado dividiendo las responsabilidades en diferentes archivos para que sea profesional, escalable y fácil de mantener:

app.py (El Cerebro y la Cara Visual): Es el archivo principal. Genera la interfaz gráfica moderna (con ventanas, botones y colores). Su función es recoger los datos del usuario, permitir arrastrar los archivos multimedia y, sobre todo, realizar los cálculos matemáticos en vivo para generar una previsualización interactiva. No procesa vídeo pesado, solo hace "los planos" de cómo debe quedar.

renderizador.py (El Músculo / Motor de Render):
Es el obrero de la aplicación. Trabaja de forma invisible en segundo plano. Cuando el usuario pulsa "Generar", este archivo coge los planos de app.py, abre los vídeos originales en alta resolución y ensambla el resultado. Contiene tecnología de exportación adaptada a estándares de televisión (como bitrates constantes de 15Mbps en H.264).

stadium_library.json (La Base de Datos):
Un archivo de texto ligero y estructurado. Funciona como una biblioteca. En lugar de que el operador tenga que teclear las medidas exactas de cada estadio de memoria (arriesgándose a fallar por un píxel), este archivo guarda los perfiles (MetLife, Bernabéu, etc.). El sistema lo lee automáticamente al arrancar. Si mañana hay un estadio nuevo, solo se añade una línea de texto aquí, sin tocar el código.

La carpeta mi_entorno (La Caja de Herramientas):
Es un entorno virtual. Contiene todas las piezas prefabricadas (librerías) que hemos usado para no tener que programar desde cero cosas complejas como "leer un pixel" o "dibujar una ventana". Se queda en el ordenador del desarrollador y asegura que el programa funcione independientemente de cómo esté configurado el resto del PC.

3. La Tecnología Usada (Librerías Clave)
El software se apoya en tecnología de código abierto puntera:

CustomTkinter & TkinterDnD: Se encargan de la "chapa y pintura". Proporcionan los botones redondeados, el tema oscuro y la capacidad de coger un archivo con el ratón y soltarlo directamente en la aplicación (Drag & Drop).

Pillow (PIL): Es el motor de procesamiento de imágenes. Se usa para fabricar la previsualización interactiva de la interfaz de manera fluida y sin consumir muchos recursos.

MoviePy: Es el encargado del montaje de vídeo. Conecta con las librerías internas del ordenador para leer, montar y comprimir los archivos de salida (.mov y .mp4).

Numpy: La verdadera joya de la corona de la V2. Es una librería de cálculo matricial avanzado. En lugar de "dibujar" el vídeo trozo a trozo, Numpy traduce los fotogramas a tablas de números y corta las franjas del System File resolviendo ecuaciones matemáticas en milisegundos. Es lo que ha reducido el tiempo de exportación de más de 1 hora a tan solo unos minutos.

4. Resumen del Flujo de Trabajo (User Journey)
Selección: El operador elige el estadio desde un menú desplegable. Todas las medidas técnicas y márgenes se autorrellenan y se bloquean por seguridad.

Carga de Assets: Se arrastran las texturas, logos (en .png o vídeo .mov) y la animación principal.

Previsualización: El software hace los cálculos y muestra instantáneamente cómo se verá el Mega Strip estirado y cómo quedará troceado y empaquetado para el servidor (System File).

Exportación Dual: Con un clic, se puede exportar el archivo maestro (Mega Strip) o el archivo troceado y comprimido listo para emisión (System File), ahorrando horas de trabajo manual en Premiere o After Effects.

1. La Memoria RAM (La "Mesa de Trabajo")
Efectivamente, tu intuición es correctísima. La RAM es crucial en este proyecto.

¿Para qué la usa? Imagina que la RAM es la mesa de una cocina. Como nuestro "Mega Strip" mide casi 40.000 píxeles de ancho, el programa necesita una mesa gigantesca para desenrollar toda esa imagen, colocar los logos, y poder verla entera antes de empezar a cortarla.

El truco de nuestra V2: Al usar Numpy, le hemos enseñado a usar esa mesa de forma inteligente. En lugar de copiar la tira gigante 11 veces (lo que colapsaba la RAM y tardaba 40 minutos), ahora la pone sobre la mesa una sola vez por fotograma y hace recortes virtuales rápidos.

2. El Procesador / CPU (El "Cocinero")
Este es el recurso que más se usa y el que define si el vídeo tarda 2 minutos o 10 minutos en renderizarse.

¿Para qué lo usa? La CPU hace dos trabajos pesados:

Ejecutar las matemáticas de Numpy para cortar las franjas milimétricamente en microsegundos.

La compresión de vídeo (FFmpeg): Cuando le dijimos al código que exportara en H.264 a 15Mbps, le dimos a la CPU la tarea de "aplastar" y empaquetar toda esa información visual en un archivo .mp4 súper optimizado. La CPU trabaja al 100% durante el render para comprimir cada fotograma.

3. El Disco Duro (La "Despensa")
Se usa al principio y al final del proceso.

¿Para qué lo usa? Para leer los vídeos originales (.mov pesados) a toda velocidad y para guardar el archivo final. Si tienes un disco SSD (sólido) en lugar de uno mecánico (HDD), el programa no sufrirá "tirones" al intentar leer los vídeos de fondo o los logos animados.

4. La Tarjeta Gráfica / GPU (¿Se usa?)
Por defecto, NO. Este es un dato técnico importante: las librerías estándar de Python que hemos usado (MoviePy y FFmpeg en su versión básica) están diseñadas para ejecutarse mediante CPU.

¿Por qué es algo bueno? Porque hace que tu herramienta sea universal. Puedes llevarte esa carpeta en un pendrive a cualquier portátil de oficina o servidor que no tenga una tarjeta gráfica potente (como las de gaming o edición) y el script funcionará perfectamente y sin dar errores de compatibilidad.
